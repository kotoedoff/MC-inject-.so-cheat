# 1.21.4 vanilla JNI names (Mojang official mappings, client_mappings 1.21.4)

Source: https://piston-data.mojang.com/v1/objects/0cf2a0b7f056da1a5a5dd99fc6dc752f33987150/client.txt
Vanilla production jar is obfuscated (`flk`, `gga`, ...), so JNI must use THESE names,
NOT yarn (`MinecraftClient`) and NOT mojmap (`Minecraft`) names.

| net.minecraft.client.Minecraft                    | `flk`     | singleton via getInstance|

| net.minecraft.client.player.LocalPlayer           | `gkx`     | `Minecraft.player`       |

## Entry chain (what jvm.cpp does)

1. `flk.Q()Lflk;` — static `getInstance()`
2. field `s` (`Lgga;`) — `Minecraft.level` (null in menu!)
3. field `t` (`Lgkx;`) — `Minecraft.player` (null in menu!)
4. `gga.d()Ljava/lang/Iterable;` — `ClientLevel.entitiesForRendering()`
5. `java/lang/Iterable.iterator()Ljava/util/Iterator;` → `hasNext/next` loop (cap 30)
6. per entity (`bum`):
   - `dA()D` / `dC()D` / `dG()D` — getX/getY/getZ
   - `bL()Z` — isAlive
   - `al()Lwp;` — getName → `wp.getString()Ljava/lang/String;` (NOT obfuscated)
   - runtime class name via `java/lang/Class.getName()` → obf name like `gkx`
   - `IsInstanceOf(playerClass coy)` → is-player flag

## Notes / risks

- `level`/`player` are null outside a world — always null-check before use.
- NEVER `FindClass` game classes during bootstrap: it forces `<clinit>` on OUR thread
  and kills the game (`Not bootstrapped`, `Rendersystem called from wrong thread`).
  Protocol: JVMTI `GetLoadedClasses` (side-effect free) until `Lflk;` appears → 20s grace
  → then resolve. Verified: baseline without inject boots fine, with early FindClass crashes.
- The dump runs on OUR background thread, game state is owned by the client thread:
  iteration is read-only + exception-guarded, fine for logging; the real ESP (step 4)
  will hook the render thread instead to avoid races.
- If Mojang renames anything in 1.21.5+, only this table + jvm.cpp change.
